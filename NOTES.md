# Recommendation System Context

- Clean architecture reference continues to follow the existing `server/src/module/*` layout used by auth/product/cart.
- Recommendation APIs are mounted under `/api/recommendations/*`, tracking under `/api/track`, analytics under `/api/analytics/recommendations`.
- Public endpoints:
  - `POST /api/track`
  - `GET /api/recommendations/home`
  - `GET /api/recommendations/product/:id`
- Protected endpoints:
  - `GET /api/recommendations/cart`
  - `GET /api/recommendations/personalized`
  - `GET /api/analytics/recommendations`
- Queue strategy:
  - publish to RabbitMQ exchange `recommendation.events`
  - consume from `recommendation_tracking_q`
  - failed jobs go to retry queue then DLQ
- Storage strategy:
  - MySQL stores canonical events, caches, similarities, embeddings metadata
  - Redis stores low-latency hot/recent signals
  - pgvector is active via `vector-db` and `ai-service`; online similarity now goes through FastAPI -> PostgreSQL vector search
- Frontend touch points already wired:
  - Home recommendation shelf
  - Product detail recommendation shelf
  - Cart recommendation shelf
  - Orders recommendation shelf
  - Thank-you recommendation shelf
- Tracking already wired for:
  - `VIEW_PRODUCT`
  - `ADD_TO_CART`
  - `SEARCH_QUERY`
  - `FAVORITE_PRODUCT`
  - `PURCHASE`
- AI service decisions:
  - FastAPI service lives in `ai-service/`
  - uses `SentenceTransformer` when available
  - falls back to hashing embeddings to keep service runnable in constrained environments
  - stores `product_embeddings` in PostgreSQL with `vector` type and queries with cosine distance
